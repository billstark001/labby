**根因判断：**跨区域连接与多次串行往返是持续高延迟的首要嫌疑，10 s 空闲回收和睡眠实例可能增加重连/冷启动成本。上述日志尚不能排除 Neon 计算资源、连接额度、DNS/网络抖动或慢 SQL；尤其 500 的确切连接失败原因仍需数据库侧指标。不要把改索引或调高超时当成已验证的修复。

### 修改计划

1. **先测量与止血。**先脱敏数据库异常中的参数，再在结构化日志中增加请求 ID、路由、池连接等待、SQL 执行、响应序列化及冷启动耗时；记录池总数/空闲/等待数。用同一时间窗对照 Neon 的连接数、计算休眠/唤醒、CPU 与查询统计，并分别测量 Railway→Neon TCP/TLS/简单查询延迟。保留故障前后分位数。评估将 API 与数据库放在同一或邻近区域的迁移，先完成连接与数据备份/回退方案，再变更生产配置。
2. **减少往返。**把外键接口按页面需要拆成有界的摘要/引用计数查询，排班历史只取 ID 或计数，详情按需加载；可并行的独立读取并行化，适合的读取改为单次 set-based SQL。人员页避免每次标签编辑后重取 230 KB 历史。测量变更前后的 SQL 次数、字节数、p50/p95。
3. **数据库侧分页。**人员/标签/关键词列表使用稳定的 SQL `ORDER BY ... LIMIT/OFFSET` 或游标分页、单独计数；必要时新增与排序/成员查询相符的列与索引。检查 `person_ids` JSONB 重叠查询的执行计划，再决定 GIN/关系表方案；不要凭猜测建索引。
4. **连接策略。**依据同区域测量和 Neon 池化端点特性设置显式池上限、合理空闲时间和连接超时，避免睡眠唤醒时并发请求形成连接风暴。保留连接失败为 5xx 并提供可重试信息。

**验收：**在相同数据量和 Railway production 路径上，普通小列表与人员外键接口记录 p50/p95、SQL 次数和响应体大小，目标先定为 p95 < 1 s 与外键数据量显著下降；连续冷启动、并发刷新及 30 分钟空闲后访问不再出现连接 `ETIMEDOUT`。若无法达到，按新测量结果重新定目标并定位瓶颈。

## 2. 默认排班算法：P1

### 当前实现与问题

- 默认路径是[模拟退火](../../packages/core/src/schedule/annealing.ts)，不是遗传算法。初始解用 DRR 选发表者、VFT 选提问者；退火有五类邻域操作，配置 `maxIter=5000`，但最佳分数连续 **80 次**无改善即停机。搜索有实质改善，却很容易早停。
- [评分函数](../../packages/core/src/schedule/constraints.ts)把**所有人的发表间隔合并**到一个数组，再计算总体均值/方差和最小、最大间隔；没有逐人相对于其目标频率的间隔损失，也不计入计划边界与历史衔接的等待时间。它可能用其他人的良好间隔抵消某个人的连续周发表。周序号而非实际日期差也会掩盖停会周、多个工作日等情形。
- 同一天 `A` 发表、`B` 提问，同时 `B` 发表、`A` 提问满足现有合法性规则。[代价计算](../../packages/core/src/schedule/constraints.ts)只惩罚重复的**有向** `提问者→发表者`，没有同日互换角色计数、目标或可调权重。当前 UI 无法鼓励或抑制这种组合。
- 可选约束主要在初始/邻域候选上起作用：`no-overlap` 被候选过滤，`affinity-boost` 改提问者抽样权重，`frequency-multiplier` 改权重/计数。然而 `constraintPenalty` 始终返回 **0**；`no-overlap.weight`、`frequency-multiplier.baseline/weight` 不进入评分。手工修改或导入的计划没有相应的终态硬约束检查。`boost < 1` 虽在类型说明中意为抑制，却缺少与目标函数一致的验证。
- [现有测试](../../packages/core/tests/algorithm.precise.test.ts)覆盖了某些固定种子下的约束结果，但没有跨种子的逐人间隔、同日互换角色、搜索增益、硬约束和时间预算指标。[算法说明](../algorithm-scheduling.md)关于初始排序、邻域数量及可选约束列表已落后于实现。

### 临时可复现实验

在 `/tmp/labby-schedule-audit.ts` 用 18 名人员、39 个每周三的 session、每次 2 名发表者/每篇 2 名提问者、无不可用、固定相似度，LCG 种子 1–12 比较初始解与当前退火解；脚本不在仓库内。在这组合成数据上，**当前目标函数分数**下降约 31%–48%，因此“搜索完全没有意义”不是直接证实的事实。但优化后仍有同日互换角色（例如种子 1、6、7、8、10、12）；把停机耐心从 80 增为 5000 后，前 6 个种子的分数又下降约 25%–39%。这说明早停确实丢失搜索空间，同时更低分仍不能证明业务质量。该实验不是生产人员/历史的统计结论；修改时应以去标识化真实规模再复验。

### 修改计划

1. 定义可解释的质量指标：每人实际日期间隔的最小值、最大值、变异系数、短于目标比例、首尾等待；按其发表频率目标归一化。对一次只有 0/1 篇者说明如何处理边界。定义同日互换角色计数及配置级偏好：禁止、抑制、中性、鼓励，明确它与同日重复角色/人数不足的优先级。
2. 把硬规则与软偏好分离。可用性、同篇自问、重复提问者、`no-overlap` 等在生成、邻域、手工编辑、导入、保存与最终验收使用同一校验；软约束进入统一的代价函数与指标解释，真正使用约束权重、基线与频率乘数。现有 JSON 约束的语义迁移需有版本和兼容处理。
3. 让搜索能修复上述指标：增加以“最差个人/短间隔/同日互换/标签约束”为目标的邻域，并保留随机大步长；对无效或原样邻居计数，采用多起点、重热或自适应停机/时间预算。把初始、最终及各项分数、实际迭代、接受率、无效邻居率和耗时输出为诊断，勿仅调 `maxIter`。
4. 建基准矩阵：不同人数、日期密度、请假、历史冻结、标签频率权重和不可满足约束；固定多种子，与当前版本比较业务指标和运行时间。新增性质测试：每人间隔下限在可满足实例成立、同日互换偏好方向正确、约束满足/冲突可解释、增量求解不改冻结历史。复杂情形需显示“无法满足”而非静默给出误导性计划。

**验收：**在预先固定的数据集/种子上，不能以总成本单项过关；逐人短间隔、同日互换计数、硬约束违规数及运行时间都需达到约定阈值。文档应披露不可满足实例及策略取舍。

## 3. 标签、约束与排班高亮：P1/P2

### 已确认

- [人员页](../../packages/web/src/pages/person/index.tsx)只有“人员/约束/用户”页签；[标签管理](../../packages/web/src/pages/person/PersonsTab.tsx)在一个容纳列表和编辑表单的 Dialog 内。新建标签颜色硬编码 `#2563eb`。人员排序选项只有名称、备注、修改时间；[列表类型](../../packages/core/src/db.ts)、服务器排序与本地 PGlite 排序也都没有标签/禁用排序。
- 三种[约束类型](../../packages/core/src/types.ts)只有 `personIds`。`affinity-boost` 把一个组内的所有配对一并提高，无法准确表示“本地人 ↔ 留学生”这类**两组之间**的共现，而不同时鼓励组内配对。标签成员目前只保存在人员 `tagIds` 中；服务器外键读取只取已引用人员的标签，不能完整代表一个约束引用的空标签。
- [排班页](../../packages/web/src/pages/schedule/index.tsx)各只有一个人员和一个标签下拉框；高亮是两者成员并集。[排班展示](../../packages/web/src/pages/schedule/ScheduleView.tsx)发表者右键菜单只在手工编辑模式出现，提问者菜单内容也只在编辑模式出现；没有高亮/仅高亮右键动作。

### 修改计划

1. 新建人员页“标签”页签，常驻可搜索、排序的标签列表，展示颜色、成员数和备注；Dialog 只负责新建/编辑，删除使用确认操作。创建时从限定饱和度与明度的 HSV 空间选随机色，转为 `#RRGGBB`，保证浅/深主题可读并允许手选；编辑沿用原颜色。
2. 人员列表增加“标签”“已禁用”排序，给多标签人员定义稳定规则（按规范化标签名排序后的首项，再按完整标签串和 ID 决胜；无标签排在末尾），禁用排序用布尔值和稳定次序。本地 PGlite 与服务器 API 的分页、总数和排序必须一致；避免只对当前页前端排序。
3. 为约束引入明确选择器（人员 ID、标签 ID 或两者组合），在求解时解析为当时的**活跃**人员集合并去重；已保存的 person-only 数据保持可读。成对约束支持单组内部或左右两组之间的配对，`A↔B` 不等同于两组的并集；频率约束支持标签目标，例如毕业生发表次数降低。明确同人属于两个标签、禁用、标签删除/改名、成员变化后重新求解、历史快照和空集合的行为。扩展持久化、校验、外键加载、API 与前端表单，并给出数据迁移/回退路径。
4. 高亮入口改成 Dialog，同时多选人员和标签，可清空、全选并选择“高亮/仅高亮”；成员集合按并集去重，仅高亮应淡化其他人而不更改排班。发表者和提问者在任何模式下右键可切换自身高亮/仅高亮，编辑模式额外显示编辑动作；菜单键盘可操作，桌面/移动视图一致。

**验收：**人员和标签排序跨页稳定；本地/服务器结果相同。分别测试人员、标签、混合、左右组选择器的三种约束及成员变化。高亮多选与右键动作在编辑开/关时一致，并有键盘与触屏可达入口。

## 4. 异步状态、邮件和 HTTP 错误：P0/P1

### 已确认

- 项目规范已有 `useAsyncResource`、`ContentSkeleton` 和内容错误重试要求，多处**初始读取**已做到。相反，[人员与标签操作](../../packages/web/src/pages/person/PersonsTab.tsx)、[约束操作](../../packages/web/src/pages/person/ConstraintsTab.tsx)、[邮件任务列表](../../packages/web/src/pages/email-task/EmailTasksListPage.tsx)、[邮件编辑页](../../packages/web/src/pages/email-task/EmailTaskEditPage.tsx)的多项保存、删除、启禁用、跳过、发送、复制操作直接启动 Promise，没有对应按钮忙碌状态或重复提交防护；部分失败仅 `void` 掉 Promise。排班生成已有 loading toast，表明可复用现有组件。
- [立即发送 API](../../packages/server/src/app.ts)无请求体收件人参数，委托的[通知器](../../packages/server/src/cron/email-task-notifier.ts)循环使用保存的 `task.emails`；[前端](../../packages/web/src/pages/email-task/EmailTaskEditPage.tsx)点按钮即发送，没有审核地址的 Dialog。通知器还会按 `recentTimes` 跳过收件人；零发送也可能返回 `{ok:true}`，造成误导性成功提示。
- [刷新令牌逻辑](../../packages/web/src/lib/auth.ts)对**任何**非 2xx 刷新响应都调用 `_invalidateSession(..., 'refresh_401')`。若原请求 401、刷新请求 500，`apiFetch` 吞掉刷新异常并返回原来的 401，UI 随后跳登录页。[通用 API](../../packages/web/src/lib/api.ts)仅按最终 401 跳转，[403 toast](../../packages/web/src/lib/api-error-toast.ts)只认真实 403；在检查过的链路中未发现直接把 5xx 变为 403。生产日志在 10:00:13 的 401 后紧跟 10:00:14 的 refresh 500，符合这个误判路径，但不能单靠日志证明浏览器当时具体显示了什么。

### 修改计划

1. 逐个盘点 `packages/web/src` 的初始读取、重取、手动变更、上传/备份、剪贴板、登录与后台同步。初始读取保留骨架屏；同键重取保持旧数据并标 `aria-busy`；每个前台动作使用按钮/行级 busy、禁重、明确成功/失败；后台同步和自动刷新用轻量状态标识。把失败反馈留在所属操作区域，恢复后才清除。先修复上面列出的人员/约束/邮件动作，再覆盖设置、用户、排班历史、图谱和备份。
2. “立即发送”先开 Dialog，默认填入当前**已保存**任务的地址列表，允许本次修改与校验，确认后发起请求；显示逐地址或汇总的真实发送结果，发送中锁定确认。一次性地址不修改定时任务收件人。后端接受并验证一次性收件人列表，明确手动发送是否绕过 `recentTimes`（建议绕过，并不更新定时发送计数），无排班/无人送达须返回可解释结果而非静默成功；权限与日志脱敏沿用现有 API 规则。
3. 刷新失败按状态分类：仅明确的 401（及定义好的不可恢复会话错误）清除令牌；403 显示权限错误；5xx/网络超时保留令牌与当前页面，显示服务暂不可用并允许重试。并发 401 共用一次刷新 Promise，避免令牌轮换竞态。刷新失败时向调用方传播真实 5xx/网络状态，不能重新包装为原始 401。增加 401→500、主动刷新 500、真正 401、403、网络失败及并发请求的回归测试。

**验收：**人为延迟/拒绝每类异步动作时，用户始终能看到进行中及最终状态，且不能重复提交；发送 Dialog 不改变保存的地址，零送达不报成功；上述 5xx 场景不会登出或显示“权限不足”。

## 实施顺序与文档收尾

1. **P0：**先加生产测量并处理跨区域/连接问题，同时修复刷新 5xx 误登出；以同一观察窗口确认变化。
2. **P1：**确定排班业务指标与约束选择器语义，补基准，再改求解器及约束持久化/API；随后实现标签页、排序和多选高亮。
3. **P1/P2：**补齐全部异步反馈与邮件一次性收件人流程；完成本地/服务器模式、三语言文案、移动端与可访问性回归。
4. 改动落地时同步更新[算法说明](../algorithm-scheduling.md)、[Railway 运维说明](../deploy-railway.md)和[工程规范](../engineering-standards.md)，报告基准、风险及不可满足场景。每个阶段独立提交并可回退；生产区域或数据库迁移另备份、演练和健康检查。
